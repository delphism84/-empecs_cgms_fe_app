1. 로그인 방법 — 현재 구현 상태

아래는 Flutter 앱(lib/) 기준입니다. 운영 서버·콘솔 설정은 별도입니다.

로그인 방법 현상태 (가능 여부, 주의사항, 삭제 예정 등)
EASY LOGIN (Google / Apple / Kakao) 현재: 앱에서 SDK로 토큰을 받아 POST /api/auth/social/verify로 JWT를 받는 흐름이 구현되어 있습니다 (social_auth_service.dart).
잔여: 레포의 Node backend에는 해당 라우트가 없을 수 있으며, 실제 동작은 운영 백엔드에 해당 API가 배포·설정되어 있어야 합니다. Google/Kakao 키는 social_auth_config.dart 및 Android/iOS 매니페스트에 반영되어 있습니다.
CREATE ACCOUNT 유지
EXISTING LOGIN (이메일/비밀번호) 유지
SIGN IN 과 GUEST LOGIN의 차이 Sign In: 입력한 ID/PW로 서버 로그인을 먼저 시도합니다. 성공 시 정상 JWT·계정 연동. 실패 시(타임아웃·소켓 등) 로컬 오프라인 로그인으로 대체(LOCAL_USER_TOKEN, guestMode = false, 입력 이메일을 사용자 식별에 사용).
GUEST LOGIN: 서버 로그인 없이 OFFLINE_USER_TOKEN + guestMode = true로 진입합니다. 저장된 lastUserId 또는 입력란의 ID를 보조 식별에 쓸 수 있습니다.
요약: Sign In은 “온라인 우선 + 실패 시 로컬 우회”, GUEST LOGIN은 “처음부터 게스트(오프라인) 모드”에 가깝습니다.
CONTINUE AS GUEST 삭제 : GUEST LOGIN과 중복
개발/테스트용 동작: IngestQueueService는 게스트 또는 빈 토큰일 때 특정 테스트 계정으로 자동 로그인을 시도하는 코드가 있습니다. 운영 정책과 맞는지 검토가 필요합니다.

1-2. 서버와 로컬 간 데이터 공유

상황 상세 부연 (코드 기준)
네트워크가 끊긴 로컬 모드에서도 로그인·테스트가 가능한가? 부분적으로 예. CONTINUE AS GUEST, GUEST LOGIN, 또는 Sign In 후 네트워크 실패 시 로컬 분기로 홈 진입이 가능합니다. 다만 실제 서버 JWT 발급이 필요한 정식 로그인은 연결이 필요합니다.
로그인 후 센서 연결로 쌓인 로컬 데이터는, 서버가 다시 연결되면 자동으로 서버에 저장되는가? 혈당은 로컬 DB 우선 저장 후 큐(IngestQueueService)를 통해 postGlucoseBatch로 업로드를 시도합니다. 서버 요청이 성공하면 큐에서 제거됩니다. 실패 시 큐에 남아 이후 재시도됩니다.
다만 서버 업로드 경로는 DataService._canUpload()에서 eqsn과 sensorStartAt이 둘 다 있어야 업로드를 진행하도록 되어 있습니다. 토큰이 게스트/플레이스홀더면 업로드가 막히거나 제한될 수 있습니다.
서버 연결 상태에서 센서 연결 성공 후, 갑자기 로그아웃/다른 계정 로그인하면 이전 로그로 센서가 자동 접속되는가? 정식 Logout(user_detail_page.dart): BLE disconnect 호출, SharedPreferences의 cgms.last_mac 제거, eqsn 등 설정 초기화 후 로그인 화면으로 이동합니다. 따라서 로그아웃 직후에는 저장된 MAC 기준 자동 재연결이 없어야 합니다.
로그아웃 없이 계정만 바꾸는 별도 경로가 있다면 그에 따라 다를 수 있습니다(현재는 로그아웃 시 BLE 메모리 초기화가 명시됨).
앱 삭제 후 재설치 시, 서버 로그인 정보만으로 로컬에 데이터가 자동 푸시되는가? 재설치 시 로컬 DB·SharedPreferences가 초기화됩니다. 로그인 후 ProfileSyncService 등으로 프로필(/api/auth/me)은 갱신될 수 있으나, 과거 전체 혈당 이력이 서버에서 자동으로 모두 내려와 복원된다는 보장은 코드만으로는 단정하기 어렵고, 서버의 데이터 풀 API·앱의 시드/동기 로직 구현 범위에 따릅니다.
새로 설치했는데 이전 접속 기록으로 자동 연결이 되는 것이 맞는가? 일반적으로 아니오. BLE 마지막 주소는 cgms.last_mac(SharedPreferences)에 저장되며, 앱 삭제 시 함께 사라집니다. 재설치 직후에는 값이 없어야 합니다.
예외: OS 백업/복원으로 SharedPreferences가 복원되거나, 사용자가 재설치 전에 동일 기기에서 로그아웃 없이 데이터가 남아 있는 경우 등은 환경에 따라 다를 수 있습니다.
서버 연동이 일시적으로 안 될 때 저장·호출 관계 저장: 혈당·이벤트는 로컬 저장소(GlucoseLocalRepo, EventLocalRepo)에 우선 기록되는 경로가 많습니다.
업로드: 가능할 때 API 호출; 실패 시 큐/로컬 유지.
호출: API 타임아웃은 DebugConfig.apiTimeoutMs 등으로 제한됩니다. 완전 오프라인이면 서버 조회는 실패하고 로컬 캐시·화면 로직에 의존합니다.

1-3. 센서 측정 종료 상황

상황 상세 부연 (코드 기준)
센서 연결 후 15일이 지나면 연결 종료는 어떻게 이뤄지는가? (센서 disconnect? 앱 자동 종료?) 앱 상수 AppConstants.defaultSensorValidityDays = 15로 남은 일수·UI·리포트 범위 등에 사용됩니다 (main_dashboard.dart 등).
15일 도래 시 BLE를 앱이 자동으로 끊는다는 전용 로직은 검색상 핵심 플로우에 명시되어 있지 않습니다. 만료 안내 문구·알림 타입(alert_engine.dart의 expired 등)과 사용자 안내(sensor_remove_page.dart 등)는 있습니다.
실제 물리 연결 해제는 사용자가 앱에서 Disconnect 하거나, 주변 환경에 따른 BLE 끊김 시 기존 disconnect 처리(알림, 자동 재연결 폴링 등)를 탑니다.
사용 중 데이터 이상 등으로 센서가 강제 disconnect를 보내면 앱 흐름은? BLE 연결 상태가 disconnected로 오면: RSSI 감시 중지, 연결 단계 초기화, (조건 충족 시) 시그널 로스 알림, cgms.last_mac가 있으면 자동 재연결 폴링(주기적으로 tryAutoReconnect)이 동작합니다 (ble_service.dart).
사용자가 앱에서 연결 해제한 경우(_userInitiatedDisconnect)는 링크 알림 등이 다르게 처리될 수 있습니다.
